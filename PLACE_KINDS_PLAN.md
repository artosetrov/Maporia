# Maporia: Locations / Services / Experiences

План введения трёх типов карточек в Maporia. Применённое в этом раунде помечено как ✅ DONE.

## 1. Архитектурное решение

Одна таблица `places` + дискриминатор `kind`:

- `kind = 'location'` — текущие места на карте.
- `kind = 'service'` — услуги (фотограф, инструктор, массаж). Цена + режим.
- `kind = 'experience'` — впечатления в стиле Airbnb (тур, мастер-класс). Цена + длительность + расписание.

Почему одна таблица, а не три:

- Все три имеют одинаковый «корпус»: фото, заголовок, описание, гео, категории, теги, владелец.
- Все три ходят на карту, в фильтры, в избранное, в коллекции — переиспользуем все существующие индексы, RLS-политики, страницы редактирования.
- Сервисы и впечатления отличаются от локаций только дополнительными полями (цена, длительность, расписание) и **дизайном страницы** места.
- Если в будущем добавится бронирование — отдельная таблица `bookings(place_id)` всё равно ссылается на `places`.

## 2. Схема БД ✅ DONE

Применённая миграция `add_place_kind_and_pricing_fields`:

```sql
ALTER TABLE public.places
  ADD COLUMN kind text NOT NULL DEFAULT 'location'
    CHECK (kind IN ('location','service','experience'));
CREATE INDEX places_kind_idx ON public.places (kind);

ALTER TABLE public.places
  ADD COLUMN price_amount    numeric(10,2),
  ADD COLUMN price_currency  text DEFAULT 'USD',
  ADD COLUMN price_unit      text
    CHECK (price_unit IS NULL OR price_unit IN
      ('fixed','from','per_hour','per_person','per_day','per_session')),
  ADD COLUMN duration_minutes integer
    CHECK (duration_minutes IS NULL OR duration_minutes > 0),
  ADD COLUMN schedule jsonb;

UPDATE public.places SET kind = 'location' WHERE kind IS NULL OR kind = '';
```

Бэкфилл прошёл — все 292 существующих места стали `kind='location'`, ничего не сломалось.

`schedule` — JSON с понятными формами:

```json
{ "type": "weekly", "days": ["mon","tue","wed"], "from": "10:00", "to": "18:00" }
{ "type": "dates",  "dates": ["2026-06-01","2026-06-08"] }
{ "type": "on_request" }
```

JSON выбран намеренно — расписание у разных карточек разное; жёсткая схема загнала бы нас в один формат и потом пришлось бы добавлять колонки.

## 3. Что сделано в коде ✅ DONE

- Поля `kind/price_*/duration_minutes/schedule` добавлены во все три варианта (Row/Insert/Update) таблицы `places`.

### `/add` — выбор типа
`app/(auth)/add/page.tsx` переписан:

- Поддерживается прямой переход `?kind=location|service|experience` для пресетов и deep-links (например, кнопки на лендинге «Создать услугу»).
- Премиум-гейт и authn остались на месте.

### Страница места
`app/id/[id]/page.tsx`:
- Загружает `kind` и новые поля в `select`.
- В типе `Place` появились эти поля.
- После загрузки данных, до основного `return` стоит kind-router: для `service` и `experience` рендерится новый компонент `OfferPlaceView`. Локации продолжают работать через старый код.

`app/id/[id]/_views/OfferPlaceView.tsx` — новый шаблон в стиле Airbnb Experience:
- Hero с обложкой, чипом типа («🛠 Услуга» / «✨ Экспириенс»), кнопками назад/в избранное.
- Три плитки фактов: цена (форматированная с символом валюты), длительность (часы:минуты), расписание (Пн, Вт, 10:00–18:00 / даты / по запросу).
- Описание, категории/теги, мини-карта (только если есть `lat/lng`).
- Sticky CTA внизу: цена + кнопка «Связаться» (для service) / «Забронировать» (для experience). CTA ведёт на `place.link`, если он указан, иначе кнопка дизейблится.

## 5. Известные риски

- **Карта**: текущий select на `/map` не тянет `kind`. Для MVP это норм — все услуги и впечатления просто появятся на карте как обычные точки. Но как только понадобится отдельный layer/фильтр — `kind` нужно добавить в select и фильтрацию.
- **Photo Tour**: `OfferPlaceView` показывает только обложку. Если у service/experience будут добавляться фото в `place_photos` — их пока не видно. Расширим, когда понадобится.
- **Цены и валюты**: сейчас в БД свободно — `numeric(10,2)` + строка валюты. Нет валидации того, что валюта существует. Окей для MVP, но если пойдём в платежи — нужен whitelist.
- **`schedule` как `Json`**: TypeScript-уровень не проверит форму. На время разработки `OfferPlaceView` сам аккуратно разбирает структуру. Если бизнес-логика расписания усложнится, стоит вынести в `app/types/place.ts` отдельный union-тип со zod-валидатором.
