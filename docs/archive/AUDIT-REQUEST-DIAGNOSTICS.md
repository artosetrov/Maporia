# Аудит запросов (safe mode) — диагностика перегрузки браузера

**Дата:** 2026-01-29  
**Цель:** Найти причину перегрузки (ERR_INSUFFICIENT_RESOURCES) без изменения поведения.

---

## 1. Зависимости useEffect (без изменений, только фиксация)

### useUserAccess.ts
- **Эффект:** session + profile.
- **Зависимости:** `[requireAuth, requireProfile]`.
- **Примечание:** Хук вызывается в **нескольких компонентах на одной странице** (TopBar, BottomNav, страница, модалки). Каждый вызов = отдельный эффект = отдельные запросы `getSession()` и `profiles.select()`. Дублирование по количеству компонентов, использующих хук.

### map/page.tsx — загрузка мест
- **Эффект:** запрос places в Supabase.
- **Зависимости:** `[bootReady, placesLoading, placesData?.length ?? 0, filteredPlaces.length]`.
- **Потенциальная проблема:** В зависимостях есть `filteredPlaces.length`. При изменении только клиентской фильтрации (без смены URL/фильтров) меняется длина списка → эффект перезапускается → повторный запрос places к серверу. То есть рефетч может срабатывать не только при смене фильтров, но и при изменении длины отфильтрованного списка.

### map/page.tsx — loadUser
- **Эффект:** `loadUser()` (getUser + профиль).
- **Зависимости:** `[]` (один раз при монтировании).
- **Дублирование:** На странице также вызывается `useUserAccess()`, который делает getSession + профиль. Получается два набора запросов на одну и ту же сессию/профиль.

### explore/page.tsx — загрузка мест
- **Эффект:** запрос places.
- **Зависимости:** `[selectedCities, selectedCategories, q, selectedTag]`.
- **Готовность auth:** Эффект не ждёт `accessLoading`. Запрос places уходит сразу при монтировании, параллельно с useUserAccess. Не обязательно ошибка, но запросы идут до готовности auth.

### explore/page.tsx — loadUser
- **Эффект:** `loadUser()`.
- **Зависимости:** `[pathname]`.
- **Дублирование:** Как и на map, есть useUserAccess + отдельный loadUser → два набора запросов сессия/профиль. Плюс при каждом изменении pathname loadUser вызывается снова.

### feed/page.tsx — пользователь и профиль
- **Эффект (первый):** `getUser()` + `profiles.select("display_name, avatar_url")`.
- **Зависимости:** `[]`.
- **Дублирование:** На странице вызывается `useUserAccess()` (session + profile). Получается дублирование запросов сессии и профиля. Эффект не ждёт accessLoading.

### feed/page.tsx — активности
- **Эффект:** `loadActivities()` (places, likes, comments).
- **Зависимости:** `[pathname]`.
- **Готовность auth:** Не проверяет `userId` / `accessLoading`. Запрос уходит при монтировании и при смене pathname, независимо от готовности auth.

### app/page.tsx (Home) — избранное
- **Эффект:** загрузка favorites (reactions).
- **Зависимости:** `[userId]`.
- **Порядок:** Запрос идёт только после появления userId (из useUserAccess). Ожидание auth соблюдено.

### app/page.tsx — bootstrap
- **Эффект:** `setBootReady(true)` при `!accessLoading`.
- **Зависимости:** `[accessLoading, user, profile, access]`.
- Секции рендерятся после bootReady, то есть после готовности auth — ок.

### id/[id]/page.tsx — место, создатель, комментарии
- **Эффект:** place + creator profile + comments + counts.
- **Зависимости:** `[id, router]`.
- **Готовность auth:** Не ждёт accessLoading. Запросы place/creator/comments уходят сразу при монтировании — для публичной страницы места допустимо.
- **Дублирование:** Отдельный эффект с `[]` делает getUser + профиль текущего пользователя — дублирует useUserAccess на этой же странице.

### PlaceCard.tsx — профиль создателя и фото
- **Эффекты:** загрузка creator profile и place_photos.
- **Зависимости:** `[place.created_by, isInView]` и `[place.id, place.cover_url, isInView]`.
- **Когда запрос не идёт:** Пока `isInView === false`, запросы не выполняются (показывается только cover_url). Для карточек, которые пользователь так и не доскроллил, запросы действительно не вызываются — это ожидаемое поведение для ленивой загрузки.

### HomeSection.tsx — места по секциям
- **Эффект:** загрузка мест для секции (в т.ч. recommended с доп. запросом профиля по интересам).
- **Зависимости:** `[section.*, categoriesKey, userId, userAccess, refreshKey]`.
- На главной секции рендерятся после bootReady (userId/userAccess уже есть), поэтому запросы после готовности auth. При этом количество секций = количество параллельных запросов мест (и при необходимости профиля для recommended).

## 2. Запросы до готовности auth/session/profile

| Место | Что происходит |
|-------|----------------|
| **feed/page.tsx** | `loadActivities()` вызывается по `[pathname]` без проверки userId/accessLoading. Запросы places/likes/comments могут уходить до готовности auth. |
| **explore/page.tsx** | Загрузка places по `[selectedCities, selectedCategories, q, selectedTag]` без проверки accessLoading. Запрос places идёт сразу при монтировании. |
| **id/[id]/page.tsx** | Загрузка place/creator/comments по `[id, router]` без проверки accessLoading. Для страницы места это приемлемо (публичный контент). |

Остальные страницы (map, home, saved, edit-страницы) либо ждут `bootReady`/`accessLoading`, либо проверяют `userId`/`user` перед запросами.

---

## 3. Дублирующиеся запросы

| Страница/контекст | Дублирование |
|-------------------|--------------|
| **Любая страница с TopBar/BottomNav** | useUserAccess вызывается в layout/странице и в TopBar (и при наличии в BottomNav). Каждый вызов = свои getSession() + profiles.select(). Итого 2–3 набора одинаковых запросов на одну страницу. |
| **map/page.tsx** | useUserAccess (session + profile) + loadUser() (getUser + profile). Два набора запросов на сессию/профиль. |
| **explore/page.tsx** | То же: useUserAccess + loadUser() по pathname. Два набора + повтор при смене pathname. |
| **feed/page.tsx** | useUserAccess + отдельный эффект (getUser + profiles). Два набора запросов сессия/профиль. |
| **id/[id]/page.tsx** | useUserAccess + эффект с getUser + profiles в `[]`. Два набора запросов профиля текущего пользователя. |

Объединять или удалять запросы по условию аудита нельзя — только фиксация.

## 4. Места, где запрос может не вызваться вообще

| Место | Условие |
|-------|---------|
| **PlaceCard** | Профиль создателя и фото: запросы выполняются только при `isInView === true`. Если карточка никогда не попадает во viewport (например, пользователь не скроллит до конца списка), запросы не выполняются. Это задумано (ленивая загрузка). |
| **HomeSection (recommended)** | Если `userId` ещё null (например, из-за порядка рендера), блок recommended может не загрузить данные по интересам или загрузить без учёта пользователя. На главной bootReady обычно ставится после useUserAccess, поэтому userId к моменту рендера секций уже есть. |
| **saved/page.tsx** | Загрузка сохранённых мест в эффекте с `[!accessLoading && userId]`. Если пользователь не залогинен, useUserAccess сделает redirect на /auth; иначе запрос пойдёт после появления userId. Запрос не вызывается только для гостя (ожидаемо). |

Явных багов «запрос никогда не выполнится при корректных данных» по коду не видно; основная особенность — ленивая загрузка в PlaceCard по isInView.

## 5. Итог по перегрузке браузера

- **Множественные вызовы useUserAccess:** на каждой странице хук вызывается в странице + в TopBar (и при необходимости в других компонентах). Каждый вызов даёт свои getSession + profile → 2–3 и более одинаковых запросов на загрузку.
- **Дублирование с loadUser / отдельным getUser+profile:** на map, explore, feed, id/[id] те же данные (сессия/профиль) запрашиваются ещё раз через loadUser или локальный эффект.
- **Много параллельных запросов с карточек:** каждая видимая PlaceCard запрашивает creator profile + place_photos. При большом количестве карточек в viewport (до введения isInView было ещё больше) это даёт десятки одновременных запросов. Сейчас ограничено isInView, но при быстром скролле или большой высоте viewport число одновременных запросов всё ещё может быть большим.
- **Map/explore:** загрузка фото мест в цикле по всем places (последовательно) + при большом списке мест множество маркеров/карточек может усугублять нагрузку в сочетании с остальными запросами.
